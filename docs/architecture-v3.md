# 架构 v3（规划中）：取消入库，阅读直接从 JM 取，DMIT 只做缓存

状态：2026-10-25 定下方案，**尚未实施**。现在线上运行的仍是 [architecture.md](architecture.md) 描述的结构（入库到书库频道，从频道按页读取）。本文是下一次大改动的设计依据，实施时按第 11 节分步进行。

## 1. 目标

- **DMIT 的流量尽量少。** DMIT 服务器按上下行双向计费，之前的结构里一本漫画要在 DMIT 上进出好几次。
- **收藏只管收藏夹。** 收藏不再触发入库、生成 PDF 或任何任务。
- **上传精选是单独的操作。** 想在 Telegram 里长期保存、离线看的作品，才转成 PDF 发到精选频道。
- **不再有“入库”，也不再读写书库频道。**

## 2. 已确定的决定

| 项目 | 决定 |
| --- | --- |
| 入库 | 取消。Bot、Mini App、命令行里的入库和批量入库都去掉 |
| 书库频道 | 不再读写：阅读不从它读，也不作为 JM 取不到时的后备；已有帖子留在频道里不动 |
| 阅读的数据来源 | 打开时由 DMIT 从 JM 下载，边下边看，存在 DMIT 的缓存里 |
| DMIT 缓存 | 上限 2GB；超过 7 天没打开的章节删除；超过上限时按最久没打开的先删 |
| 收藏 | 只记收藏夹，包括 JM 收藏夹同步；不触发下载、PDF 或任何任务 |
| 上传精选 | 单独的按钮和任务：用缓存里的图片生成 PDF，上传到精选频道；缓存不全时先从 JM 补下 |
| Telegram 上传 | 只在 DMIT 上做，不在远程下载机上放 Telegram 凭证 |
| 搜索页封面 | 保持现状，由 DMIT 代取 JM 封面 |
| 图片的浏览器缓存 | `max-age` 24 小时（已改） |

## 3. 为什么这样省流量

之前的结构把 Telegram 书库频道当远程硬盘：入库时花一次上传流量把 CBZ 存进去，之后每次阅读，再把它从 Telegram 取回 DMIT、发给手机。JM 本身就能随时提供这些图片，而且 JM 原图比我们重新压缩后的 CBZ 更小。所以去掉书库频道这一层，直接从 JM 取，每一种场景都更省。

**换算关系（实测）：**

- “1 份”指一本漫画打包成 CBZ（WebP 质量 90）的大小。
- JM 原图约 0.77 份。三本实测比例为 1.29–1.34，见 [environment.md](environment.md) 第 9 节。
- PDF（JPEG 质量 85）约 1.25 份。现有 3 个 PDF 共 71MB，对应的 CBZ 共 57MB。

**DMIT 的流量（入站加出站）：**

| 场景 | 之前的结构 | v3 |
| --- | --- | --- |
| 第一次在 Mini App 看完一本 | 入库 1.8 + 阅读 2 = **3.8 份** | JM 下载 0.8 + 发给手机 1 = **1.8 份** |
| 缓存过期后重看 | Telegram 取回 1 + 发给手机 1 = 2 份 | JM 重新下载 0.8 + 发给手机 1 = 1.8 份 |
| 缓存还在时重看 | 1 份（只有发给手机） | 1 份 |
| 同一台手机 24 小时内重看 | 0（走手机缓存） | 0 |
| 看过之后上传精选 | Telegram 取回 1 + 上传 PDF 1.25 = 2.25 份 | 只上传 PDF，**1.25 份** |
| 没看过直接上传精选 | 要先入库：1.8 + 2.25 ≈ 4 份 | JM 下载 0.8 + 上传 PDF 1.25 ≈ 2 份 |
| 在 Telegram 里看精选 PDF | 0（Telegram 直接发给手机） | 0 |

以 JM1085296（364 页，CBZ 46.5MB）为例：之前入库加看一遍约 177MB，v3 约 84MB。

**还剩下的流量大头**是“发给手机的 1 份”，也就是 DMIT 把解码后的 WebP 传给手机。以后可以再压，见第 12 节，本次不做。

## 4. 数据流

```text
手机（Telegram 客户端 + Mini App）
  │  Mini App：接口、图片                     ▲ 精选 PDF：Telegram 直接发给手机
  ▼                                           │（不经过 DMIT）
Cloudflare ──► nginx ──► DMIT 上的 jmcomic 服务 ──► Telegram 精选频道
                          │  ▲                      （只有“上传精选”往这里传）
                          ▼  │
                         JM 接口 + JM 图片 CDN（阅读、精选的唯一数据来源）
```

书库频道不在图里，v3 不再读写它。

## 5. 阅读

### 5.1 打开一章

- `GET /api/chapter/{photo_id}` 不再查 `chapters` 表，改为从 JM 取章节详情：页数、每页文件名、所属作品、上一章和下一章。复用 `jm.py` 里已有的进程内缓存，避免重复请求。
- 返回页数，以及已经在缓存里的页的尺寸，没缓存的页尺寸为空。前端先用占位比例（例如宽高比 1:1.4）排版，图片加载后按实际尺寸调整。翻页模式不受影响。
- 同时通知下载器开始准备这一章（见 5.2）。

### 5.2 按需下载，往后预读一段

不一次下完整章，避免读几页就退出时白下几百页。

- 每个正在看的章节有一个下载器，运行在低优先级（`nice`）的子进程里，免得占住单核 CPU、拖慢 Bot 和阅读页。它保持 jmcomic 客户端和章节详情（图片地址、打乱参数），按页下载并解码。
- 主进程把读者请求到的页码告诉下载器，下载器只保证“当前页往后 N 页”（默认 20 页）已下载。读者往后翻，这个窗口就往后移。
- 2 分钟没有新请求，下载器退出；下次打开时重新启动。
- `GET /img/{photo_id}/{n}`：缓存里有就直接返回；没有就让下载器先下这一页，等它下好（最多等 30 秒，超时返回 503，前端稍后重试）。
- 同时最多 2 个下载器，例如上一章还没退出时又打开了下一章。

下载、解码单页的代码沿用 `fetch.py`：jmcomic 解码后按 WebP 质量 90 保存。

### 5.3 缓存目录和清理

- 目录：`/var/lib/jmcomic/cache/pages/<photo_id>/0001.webp`……，每章另记最近一次打开的时间。
- 清理时机：服务启动时，以及之后每小时一次。
  1. 删掉超过 `JM_CACHE_DAYS`（默认 7）天没打开的章节。
  2. 总大小仍超过 `JM_CACHE_MB`（默认 2048）时，按最近打开时间从旧到新删，直到降到上限的 90%。
- 正在下载或正在生成 PDF 的章节加锁，不会被删。
- 现在从频道按页读取用的页面缓存（`JM_CACHE_MB`，上限 1GB）由这一套取代。JM 封面缓存（最多 5000 张）保持不变。

### 5.4 JM 取不到时

- 直接提示“JM 暂时取不到这一章”，不回退书库频道。
- jmcomic 出错时，照旧请求自动更新服务检查新版本。
- 想在 JM 下架后仍能看的作品，就上传精选。

## 6. 收藏和书架

- 收藏只改 `folders`、`folder_items`，包括 JM 同步的“JM·”收藏夹。Bot、Mini App、JM 收藏夹同步都不再建任务。
- 收藏一本时，从 JM 取作品详情，写进 `albums` 表（只存元数据），并下载封面（几十 KB）。这样书架能显示标题和封面。
- 反向同步到 JM（可选开关，默认关）保留不变。
- 书架列出“收藏的作品 + 读过的作品”（`progress` 表里有的），不再按是否入库列出。筛选改为：全部、已收藏、未收藏（读过但没收藏）。
- 作品页的状态改为显示：收藏夹、精选（未上传 / 上传中 / 已上传）、缓存了几章。

## 7. 上传精选

- 新任务类型 `publish`，取代现在的 `favorite`（PDF）任务。Bot 和 Mini App 的作品页各有一个“上传精选”按钮。
- 已经上传过的作品不重复生成，按钮变成“查看精选”，直接打开原帖。
- 流程：
  1. 取作品的全部章节。逐章检查缓存，缺页时从 JM 整章补下（这里不用预读窗口，用 `fetch.py` 一次下完）。
  2. 生成期间锁住这些章节的缓存。
  3. 图片转成 JPEG（质量 85），用 img2pdf 封装成 PDF，写入标题、作者等元数据；超过单卷上限就分卷。`pdf.py` 改为直接接收图片目录，不再需要 CBZ。
  4. 并行分块上传到精选频道，帖子附“在线阅读”按钮（打开 Mini App，从 JM 读）。
  5. 记录消息 ID、大小和 sha256，解锁缓存。之后这些章节按正常规则过期。
- 生成前检查磁盘剩余空间（沿用现在“低于 1.5GB 不接新任务”的规则）。整本长篇转换时，临时文件可能有几百 MB。
- `/remove` 只删精选频道里的帖子。

## 8. Telegram 的使用

- **精选频道：** 上传 PDF，`/remove` 时删除对应帖子。这是 v3 里唯一往 Telegram 传大文件的地方。
- **书库频道：** 不再读写。已有的帖子留在频道里不动；要清理的话，在 Telegram 里手动处理。配置项 `TG_CHANNEL_ID` 不再使用。
- **数据库备份：** 现在每天发到书库频道，v3 要换个地方，见第 13 节待确认事项。
- **Bot 会话：** 只在 DMIT 上，和现在一样。

## 9. 远程下载机（oracle）

v3 里阅读不用远程下载机：

- 边下边看需要一页一页地下，在本机做最直接。整章交给远程，要等远程下完、打包、传回，第一页会等很久。
- 远程传回的是重新压缩后的图片，比 JM 原图大约 30%，DMIT 的入站流量反而更多。

上传精选时补下长篇，倒是可以考虑交给远程以节省 DMIT 的 CPU，但流量会多约 30%。默认不用，把 `JM_REMOTE_HOST` 留空即可停用。代码保留还是删除，见第 13 节。

## 10. 数据库和代码的改动

**数据库：**

| 表 | 改动 |
| --- | --- |
| `albums` | 只存收藏或读过的作品的元数据，不再表示“已入库” |
| `chapters`、`pages` | 不再写入，阅读也不再读取。旧数据怎么处理见第 13 节 |
| `jobs` | 去掉 `archive`；`favorite`（PDF）改名 `publish`，迁移时一并改旧记录 |
| `favorites`（PDF 记录） | 改名 `picks`，含义不变 |
| `progress`、`folders`、`folder_items`、`users`、`batches` | 不变 |

页面尺寸改在下载时记录，存在缓存目录里每章一个小文件，不进数据库。

**代码：**

| 模块 | 改动 |
| --- | --- |
| `web.py` | 章节接口改从 JM 取；图片接口改读缓存或等下载器；书架接口改为收藏 + 读过；去掉入库接口，加上传精选接口 |
| 新模块（如 `cache.py`） | 缓存目录、清理、加锁；下载器的管理（启动、窗口、空闲退出、并发上限） |
| `fetch.py` | 增加按页下载的常驻模式（读标准输入里的页码），保留整章下载给精选用 |
| `jobs.py` | 去掉 `archive` 任务和远程分流；`favorite` 改成 `publish`，从缓存生成 PDF；收藏不再建任务 |
| `pdf.py` | 输入从 CBZ 改为图片目录 |
| `pack.py` | 不再打包 CBZ；只留 PDF、元数据要用的部分 |
| `tg.py` | 去掉按区间读取、整本下载；保留上传 |
| `bot.py`、`ui.py` | 去掉入库、批量入库按钮；加“上传精选”；JM 同步只镜像收藏夹 |
| `sync.py`、`meta.py` | 去掉入库和 PDF 的安排；元数据文件不再写频道消息 ID、每页偏移 |
| `webapp/static/app.js` | 去掉入库按钮和入库进度条；加“上传精选”；阅读器支持占位尺寸和“页面还没下好”的等待重试 |
| `config.py`、配置示例 | `JM_CACHE_MB` 默认改为 2048，新增 `JM_CACHE_DAYS`；`TG_CHANNEL_ID` 不再使用 |
| `deploy/jmcomic.service` | 加 `IPAccounting=yes`，用 systemd 统计服务的流量（含子进程） |
| `remote.py` 和远程部署脚本 | 停用；保留还是删除见第 13 节 |

## 11. 实施顺序

每一步都可以单独部署和验收。

1. **先能量流量：** 服务开启 `IPAccounting=yes`，`/status` 显示服务累计的入站和出站流量，先记一段时间作基线。
2. **阅读改为 JM 加缓存：** 包括下载器、缓存清理、书架改为收藏加读过。这一步之后阅读不再碰书库频道。
3. **收藏解耦：** 收藏只记收藏夹，JM 同步只镜像收藏夹。
4. **上传精选独立：** 新增 `publish` 任务、按钮、从缓存生成 PDF，复用已有的 PDF 帖子。
5. **清理：** 去掉入库、书库频道、远程分流的代码，迁移数据库，换数据库备份的目的地，清理配置项。
6. **文档：** 用 v3 的内容替换 `architecture.md`，并更新 `operations.md` 和 `progress.md`。

## 12. 以后还可以做的（本次不做）

- **把发给手机的那 1 份变小：** DMIT 直接把 JM 原图（约 0.77 份）发给手机，在 Mini App 里用 Canvas 还原打乱的图片，DMIT 也不用再解码。这需要把 jmcomic 的拼图算法移植到前端。
- **降低 WebP 质量：** 现在为了画质用 90。降到 80，发给手机的流量能少一截。

## 13. 待确认事项

1. **数据库备份发到哪里：** 精选频道（会和 PDF 帖子混在一起）、和 Bot 的私聊，或者只留在服务器本地（不推荐，服务器坏了就没了）。
2. **远程下载机：** 停用后，代码和部署脚本是保留还是删除。
3. **预读窗口：** 默认往后 20 页，是否合适。
4. **旧数据：** `chapters`、`pages` 表里入库时写的记录，是保留，还是迁移时清掉。
5. **书库频道里已有的帖子：** 默认留在频道里不动。

## 14. 风险

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| JM 下架作品、接口变化或暂时连不上 | 没缓存、没上传精选的作品看不了 | 想长期保留的上传精选；jmcomic 自动更新照旧 |
| 每次阅读都从 JM 下载，访问更频繁 | 可能被 JM 限流 | 按需下载加预读窗口，不整章预下；限制下载器数量和线程数 |
| 打开一章要先下载 | 第一页要等一两秒 | 下载器优先下读者正在看的那一页 |
| 单核 CPU 要在阅读时解码 | Bot 和阅读页可能变慢 | 下载器低优先级运行；只下窗口内的页 |
| 缓存占磁盘 | 剩余空间约 3.7GB | 上限 2GB 加 7 天过期；生成 PDF 前检查剩余空间 |
