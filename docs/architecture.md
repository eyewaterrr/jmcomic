# 架构设计（v3）

v3 取消了“入库”：阅读时由服务器从 JM 取原图、只做缓存，手机上用 Canvas 还原；收藏只记收藏夹；想在 Telegram 里长期保存的作品单独“上传精选”。2026-10-25 定方案，2026-11-08 实现。v1.1 的结构（入库到书库频道、从频道按页读取）见 git 历史里的这份文件。

测量数据见 [environment.md](environment.md)，日常操作见 [operations.md](operations.md)。

## 1. 为什么改

| 问题 | v1.1 | v3 |
| --- | --- | --- |
| 服务器流量按上下行双向计费 | 一本漫画要在服务器上进出好几次：入库上传一次，每次阅读从频道取回再发给手机 | 只从 JM 取一次原图、发给手机一次；入库那份流量没有了 |
| 服务器只有 1 核 CPU | 入库时解码、重新压缩，约 0.5 秒/页，长篇要交给远程下载机 | 服务器不解码，只转发原图；还原在手机上做 |
| 收藏会触发入库和生成 PDF | 收藏一本就占一次完整的下载和上传 | 收藏只是记下来；上传精选是单独的操作 |

## 2. 总体结构

```text
手机（Telegram 客户端 + Mini App）
  │  Mini App：接口、原图（打乱过的）      ▲ 精选 PDF：Telegram 直接发给手机
  ▼                                        │（不经过服务器）
Cloudflare ──► nginx ──► 服务器上的 jmcomic 服务 ──► Telegram 精选频道
                          │  ▲                      （只有“上传精选”往这里传）
                          ▼  │
                         JM 接口 + JM 图片 CDN（阅读、精选的唯一数据来源）
```

服务是一个进程（systemd，asyncio）：

- Telethon Bot 会话（MTProto，只走 IPv4）
- FastAPI 阅读页和接口
- 原图缓存和下载队列（`cache.py`）
- 任务队列（只有“上传精选”一种任务，串行）
- 生成 PDF 时另起一个低优先级子进程

## 3. 阅读

### 3.1 打开一章

`GET /api/chapter/{章节ID}`：

1. 从 JM 取章节详情（`jm.chapter()`，缓存 1 小时），包括每页的图片地址、扩展名和打乱参数 `num`。`num` 由 jmcomic 的 `JmImageTool.get_num_by_detail` 算出。
2. 取作品详情，用于标题和上一章、下一章，并把作品和章节信息写进数据库（读过的作品会出现在书架上）。
3. 返回每页的 `[num, 宽, 高]`。尺寸来自数据库里记过的值，还不知道的为 0。

### 3.2 图片：服务器只转发原图

`GET /img/{章节ID}/{页码}`：

- 缓存里有就直接返回；没有就马上从 JM 下载。读者正在等的页排在所有预读前面，最多等 30 秒，超时返回 503，阅读页稍后重试。
- 每次请求后，保证“当前页往后 20 页”在下载队列里。读者跳到别处后，窗口外还没开始的预读直接放弃。
- 同时最多 4 个下载（`JM_IMAGE_THREADS`），用单独的线程池，不影响搜索等接口调用。
- 返回的是 JM 原图，不解码、不重新压缩。响应头是 `Cache-Control: private, max-age=86400, immutable`：Cloudflare 不缓存，手机缓存 24 小时。
- 图片请求用请求头带登录令牌，网址里不带。令牌每次打开 Mini App 都会变，放在网址里，手机缓存就永远命中不了。

### 3.3 手机上还原

JM 的图片是把原图按行切成 `num` 条、倒序排列的。阅读页（`webapp/static/strips.js`）按同样的规则用 Canvas 把条摆回去：

- 算法和 jmcomic 的 `decode_and_save` 逐行一致。单元测试会拿 jmcomic 自己的结果和服务器端的 `images.strips()`、阅读页的 `strips.js` 三方核对。
- 没打乱的页（`num` 为 0）和 GIF 直接用 `<img>` 显示，不经过 Canvas。
- 上下滑动模式：只保留屏幕附近（上下各约 6 屏）的 Canvas，离远了就释放，长篇也不会占满手机内存。
- 尺寸还不知道的页先按 1:1.4 占位，画好后按实际尺寸调整。浏览器的滚动锚定会保持当前位置不跳。每页尺寸在服务器下载时从图片头里读出、记进数据库，第二次打开就能准确排版。

### 3.4 缓存和清理

- 目录：`<数据目录>/cache/pages/<章节ID>/0001.webp`……每章另有一个 `.opened` 文件，它的修改时间就是最近一次打开的时间。
- 清理：启动时和之后每小时一次。
  1. 超过 `JM_CACHE_DAYS`（默认 7）天没打开的章节删除。
  2. 总大小仍超过 `JM_CACHE_MB`（默认 2048）时，按最近打开时间从旧到新删，降到上限的 90%。
- 不删：正在上传精选（加了锁）、正在下载、10 分钟内刚看过的章节。
- 搜索页封面另有缓存（`cache/jmcovers`，最多 5000 张）；收藏和读过的作品的封面存在 `covers/`。

### 3.5 JM 取不到时

- 阅读页提示“JM 暂时取不到这一章”。没有频道后备：想在 JM 下架后仍能看的，就上传精选。
- 图片下载失败时丢掉缓存的章节详情（图片地址可能变了），并请求自动更新服务检查 jmcomic 新版本（6 小时内最多一次）。
- JM 连不上时，作品页仍能显示数据库里保存的信息。

## 4. 收藏和书架

- “收藏” = 作品在某个用户的任意一个收藏夹里。每个用户有一个“默认收藏夹”，可以再自建；JM 账号同步来的是“JM·”收藏夹。
- 收藏只改收藏夹，不建任何任务。新收藏的作品由后台补元数据和封面，一次一本，不扎堆请求 JM。
- 书架 = 该用户收藏的作品 + 读过的作品，最近有动静的排前面。筛选：全部、已收藏、未收藏（读过但没收藏）。
- 作品页（书架、搜索结果、任务点进来都是同一页）显示：收藏夹、精选状态（未上传 / 上传中 / 已上传）、每章的页数和是否已缓存。

## 5. 上传精选

- 作品页和 Bot 作品详情里有“上传精选”按钮。已上传的变成“查看精选”。
- 流程（`jobs.py` 的 `publish` 任务）：
  1. 取作品最新的章节列表和每章的章节详情。
  2. 锁住这些章节的缓存，逐章补齐（缓存里有的不再下载）。
  3. 子进程（`nice 10`）把原图还原后直接存成 JPEG（质量 85），用 img2pdf 封装；超过 `JM_PDF_VOLUME_MB`（默认 300）就分卷。PDF 的 Subject 元数据写 JM 号和卷号。
  4. 并行分块上传到精选频道，帖子附“在线阅读”按钮（打开 Mini App，从 JM 读）。
  5. 记录消息 ID、大小和 sha256，解锁缓存。这些章节之后按正常规则过期。
- 磁盘剩余不到 1.5GB 时不接新任务。出错自动重试 3 次，间隔逐次加长。
- `/remove JM号` 删除精选记录和帖子。Telegram 不允许 Bot 删除 48 小时以前的频道消息，这些帖子 Bot 会列出链接，需要手动删。

## 6. Telegram 的使用

| 用途 | 做法 |
| --- | --- |
| Bot 私聊 | 搜索、作品详情、收藏、上传精选、进度通知、`/status` 等命令 |
| 精选频道 | 上传精选 PDF，`/remove` 时删除对应帖子。v3 里唯一往 Telegram 传大文件的地方 |
| 书库频道 | 不再读写。v1.1 的帖子留在频道里不动，要清理就在 Telegram 里手动删 |
| 数据库备份 | 不再发到频道，见第 8 节 |

**为什么文件走 MTProto：** 官方 Bot API 上传最多 50MB，长篇 PDF 必然超限；Telethon 以 Bot 身份走 MTProto，单个文件最大 2000MB，4 路并行分块上传约 7MB/s。

## 7. 流量

“1 份”指一本漫画按 v1.1 的方式打包成 CBZ（WebP 质量 90）的大小。实测 JM 原图约 0.77 份（CBZ 是原图的 1.31 倍，见 environment.md），PDF（JPEG 质量 85）约 1.25 份。

服务器的流量（入站加出站）：

| 场景 | v1.1 | v3 |
| --- | --- | --- |
| 第一次在 Mini App 看完一本 | 入库 1.8 + 阅读 2 = **3.8 份** | 从 JM 取 0.77 + 发给手机 0.77 = **1.54 份** |
| 缓存过期后重看 | 2 份 | 1.54 份 |
| 缓存还在时重看 | 1 份 | 0.77 份 |
| 同一台手机 24 小时内重看 | v1.1 网址里带着每次都变的令牌，实际命中不了手机缓存 | 0（走手机缓存） |
| 看过之后上传精选 | 2.25 份 | 只上传 PDF，**1.25 份** |
| 没看过直接上传精选 | 约 4 份 | 0.77 + 1.25 ≈ **2 份** |
| 在 Telegram 里看精选 PDF | 0 | 0 |

服务开着 systemd 的 `IPAccounting`，Bot 的 `/status` 显示服务这次启动以来的实际入站、出站流量。

## 8. 数据与备份

SQLite 使用 WAL 模式，表结构如下：

| 表 | 内容 |
| --- | --- |
| `albums` | 收藏、读过或上传过精选的作品的元数据：jm_id、标题、作者、作品、标签、章节数。标题为空表示后台还没补上 |
| `chapters` | 章节信息：photo_id、jm_id、序号、标题、页数、每页尺寸（JSON） |
| `picks` | 精选记录：jm_id、精选频道消息 ID、大小、sha256、上传人、时间 |
| `jobs` | 任务：类型（`publish`）、作品、状态、尝试次数、错误、进度消息 |
| `folders`、`folder_items` | 收藏夹和里面的作品 |
| `progress` | 每个用户每本作品读到的章节和页码 |
| `users` | 白名单：Telegram 用户 ID、角色、阅读方式 |
| `meta` | 杂项：库结构版本、JM 同步开关、最近一次同步时间等 |
| `batches` | v1.1 批量入库留下的表，v3 不再使用 |

**元数据文件：** 每本作品在 `<数据目录>/meta/JM<号>.json` 另存一份，内容包括作品信息、章节、精选记录、所在收藏夹，变化时自动更新。迁移时用 `restore-meta` 重建数据库，v1.1 的旧格式也能恢复。

**数据库备份：** 服务器的整机备份包含数据库快照和配置，服务本身不再往 Telegram 发备份。v1.1 的频道备份有个问题：每次发完新备份要删最旧的一份，可 Bot 删不了 48 小时以前的频道消息，删除失败后每小时重发，一直没停。

## 9. 安全

- **密钥不进仓库：** 本仓库是公开的。Token、api_hash、频道 ID、用户 ID、会话文件、数据库一律不提交，放在服务器的配置文件（640 权限）里，由 systemd 的 `EnvironmentFile` 加载。
- **白名单：** 所有者的 Telegram 用户 ID 写在配置文件里；其他用户由所有者在 Bot 里增删。白名单以外的人发消息，Bot 不回应。
- **Mini App 登录：** 页面把 Telegram 提供的 `initData` 发给服务器，服务器校验 HMAC 签名、`auth_date` 是否过期、用户是否在白名单里，然后发一个 12 小时有效的令牌。之后所有接口和图片都要带这个令牌。
- **对外：** 服务只监听 127.0.0.1；nginx 只放行 Cloudflare 回源。图片接口按章节 ID 和页码访问，不暴露服务器上的文件路径。
- **服务权限：** 专用系统用户运行，`NoNewPrivileges`、`ProtectSystem=strict`，`MemoryMax` 限制内存。

## 10. 资源预算

本机有 1 vCPU、1.9GB 内存。

| 项目 | 预算 |
| --- | --- |
| 主服务常驻内存 | 约 100–150MB |
| 阅读时的 CPU | 只有网络传输和写文件；解码在手机上 |
| 生成 PDF 的子进程 | 按卷处理，峰值约 300MB；systemd 总上限 900MB |
| 原图缓存 | 2GB，7 天没打开的章节删除 |
| 磁盘保底 | 剩余空间低于 1.5GB 时暂停接新任务 |

## 11. Bot 交互与消息格式

**命令：**

- `/search 关键词`，或直接发关键词：搜索结果，已收藏的会标出来。
- 直接发 JM 号：带封面的作品详情，下方有在线阅读（或继续阅读）、收藏 / 取消收藏、上传精选 / 查看精选、作者按钮。各种写法的识别规则见 `jmshelf/ids.py`。
- 一条消息里有多个 JM 号：列出每本的标题和状态，下面有“全部收藏”。
- `/author 作者名`：按作者搜索，每次 10 本，可以“加载更多”。
- `/library`：打开 Mini App 书架。`/jobs`：最近的任务。
- 所有者专用：`/status`（版本、磁盘、缓存、流量、队列、自动更新）、`/jmsync`、`/users`、`/adduser`、`/deluser`、`/remove`。

高级搜索（按作品、标签、角色搜，排序，排行榜，分类浏览）只在 Mini App 的搜索页做，Bot 的搜索结果下面有“在书架里搜索”按钮。

**消息格式**（与本人其他 Bot 保持一致）：不使用表情符号；表格放在 `<code>` 里，表头下面一行虚线，列之间空两格，数字右对齐，表格里只用 ASCII 字符，中文说明写在表格外。

## 13. JM 收藏夹同步与自动更新

### JM 收藏夹同步（`jmshelf/sync.py`）

- **账号：** 把 JM 账号写进服务器配置的 `JM_USERNAME`、`JM_PASSWORD`，密码只保存在这台服务器上。
- **手动同步：** `/jmsync` 先登录，列出每个收藏夹的本数，以及有多少本这边还没有记录。确认后才开始。
- **规则：** 单向镜像，从 JM 到本地。JM 里的每个收藏夹对应本地一个“JM·<名字>”收藏夹，不在任何收藏夹里的归到“JM·未分类”。JM 那边移除的作品、删掉的收藏夹，本地也跟着移除。本地自建的收藏夹和精选不受影响。
- **v3 的变化：** 同步只改收藏夹，不下载、不生成 PDF。新出现的作品由后台补标题和封面。
- **自动同步：** 在 `/jmsync` 里可以打开“每天自动同步”。失败时在私聊里提醒。

### 反向同步到 JM（默认关闭）

- 开关在 `/jmsync` 的消息里，由所有者控制。打开后，所有者在这边新收藏一本时，会在后台加进 JM 账号的收藏。只加不删，其他用户的收藏不推送。
- JM 移动端的收藏接口是“切换”：对已收藏的作品再调用会先取消。所以每次推送前先读一遍 JM 现有收藏，已收藏的跳过。接口不支持指定收藏夹，新加的都进默认收藏。

### jmcomic 自动更新（`deploy/jmcomic-update.sh`）

- 每天 04:30 检查；从 JM 下载出错时，服务写一个请求文件，由 `jmcomic-update.path` 立即触发一次检查（6 小时内最多一次）。
- 只自动升级同一个大版本内的新版本，大版本只私聊提醒。
- 步骤：等正在执行的任务结束（最多 30 分钟）→ 停服务 → 升级 → 运行自检 `python -m jmshelf.selftest`（搜索、取详情、下载两张原图并还原）→ 通过就启动，不通过就装回原版本再启动。
- 结果写入 `update-status.json`，`/status` 里能看到。

## 14. 从 v1.1 升级

服务启动时打开数据库，发现是 v1.1 的结构就自动迁移：

1. 在同一目录先留一份完整备份 `jmshelf-pre-v3.db`。
2. `chapters` 只留章节信息，v1.1 记下的每页尺寸折进 `dims` 字段（这些章节第一次打开就能准确排版）；删除 `pages` 表。
3. PDF 记录表 `favorites` 改名 `picks`；入库任务删除，`favorite` 任务改名 `publish`。
4. v1.1 里只入库、既没收藏也没读过的作品，v3 的书架上看不到，放进所有者的默认收藏夹。
5. 删除频道备份的记录；重新导出全部元数据文件；删除 v1.1 的旧页面缓存（`cache/<章节ID>/`）。
