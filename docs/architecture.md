# 架构设计（v2 建议稿）

本文根据目标服务器的实测结果（见 [environment.md](environment.md)）修订 README 初版规划。标“待确认”的地方需要项目负责人决定，汇总在 [progress.md](progress.md)。

## 1. 与初版规划的主要差异

| 项目 | 初版 | 建议 | 原因 |
| --- | --- | --- | --- |
| 频道文件读写 | Bot API（HTTP），评估自建 Bot API Server | Bot 账号直接走 MTProto（Telethon） | 官方 Bot API 上传最多 50MB、下载最多 20MB，长篇必然超限。自建 Bot API Server 要编译 TDLib，读文件时也要先把整个文件落盘，本机只剩约 5GB 磁盘。MTProto 下 Bot 能上传 2000MB，并能从指定偏移开始下载。 |
| 云端阅读 | 未缓存时先取回整本再解压 | 按页从频道读取字节区间 | CBZ 不压缩打包时，每页在文件里是连续的一段。入库时记下偏移，阅读时只取这一页。首次打开不用等整本下载，也不需要大缓存。 |
| 阅读器 | 复用或改造 jm-view-server | 自研轻量阅读页（Telegram Mini App） | jm-view-server 面向本地文件夹和局域网，带删除、重命名等文件管理功能。要接 Telegram 存储，得先把整本解压到本地。它的阅读交互可以参考。 |
| Bot 框架 | python-telegram-bot | Telethon 同时负责对话和文件 | 存储层本来就要用 MTProto，这样只需一个库、一个连接。Telethon 默认只走 IPv4，正好避开本机 IPv6 到阿姆斯特丹的故障。 |
| 内容获取 | jmcomic | jmcomic，只用 API 端，图片线程 2–4 | 本机访问网页端返回 403，API 端正常。1 vCPU 下解码是瓶颈，8 线程不比 4 线程快，内存却多用近一倍。 |
| 精选收藏 | Google Drive，格式未定 | PDF 发到第二个私有频道（精选频道） | 不花钱，不用开新账号，在 Telegram 里就能直接看，上传速度也已实测过。代价是它和书库都放在 Telegram 上，算不上独立备份。 |
| 部署 | VPS | VPS 上一个 systemd 服务加若干子进程；对外复用现有 nginx 和 Cloudflare 源站证书 | 只有一个用户，单进程最简单；本机已有“只允许 Cloudflare 回源”的配置。 |

## 2. 总体结构

```text
安卓 Telegram
  ├─ 与 Bot 对话：搜索、入库、收藏、任务进度
  └─ Mini App 阅读页 https://jm.<域名>        子域名待确认
            │ HTTPS，经 Cloudflare 代理
       nginx：源站证书，只放行 Cloudflare 回源
            │ 127.0.0.1
┌──────────── jmcomic 服务（单进程 asyncio，systemd）────────────┐
│ Telethon Bot 会话（MTProto，IPv4）   FastAPI（阅读接口 + 静态页） │
│ 任务队列（SQLite 持久化，串行执行）  页面读取（区间下载 + 小缓存）│
└──────┬─────────────────────┬─────────────────────────┬────────┘
       │ 子进程              │ MTProto                 │ 子进程 + MTProto
  jmcomic 下载/解码     书库频道（私有）             PDF 转换 → 精选频道（私有）
  （API 端）            CBZ 归档 + 每日数据库备份      （精选收藏）
```

**为什么只用一个进程：**

- 只服务一个人。
- Telethon 的会话文件同一时间只能被一个进程使用。

**为什么下载放进子进程：** jmcomic 是同步的多线程库，实测峰值内存 300–530MB。放进子进程可以单独限制内存，崩溃时也不会拖垮 Bot。

## 3. 存储格式

- 一章（JM 的 photo）一个 CBZ。只有一章的作品就是一本一个文件。
- 用 `zipfile.ZIP_STORED` 打包，不压缩。WebP 和 JPEG 本身已经压缩过，再压也省不了多少；不压缩时每页数据是连续的，可以按字节区间单独读取。
- 文件名依次为 `0001.webp`、`0002.webp`……，另附 `ComicInfo.xml`，写入标题、作者、标签、页数和来源链接。这是 Mihon、Komga、Kavita 等阅读器通用的元数据格式。
- 入库时把每页的数据偏移和长度写入 SQLite 的 `pages` 表。
- 单个文件最大 2000MB（Bot 通过 MTProto 上传的上限），超过就分卷，这种情况很少见。
- CBZ 以文件消息发到频道，附 320px 封面作缩略图。消息说明的格式如下：

```text
[JM1485198] 标题
53 页 · 27.1MB
#JM1485198
```

说明里只放给人看的内容。程序要用的信息都在文件里，数据库丢失时可以靠它们从频道重建索引（见第 7 节）：

- CBZ 里的 `ComicInfo.xml` 写有 JM 号、章节 ID、章节序号和页数。
- PDF 的 Subject 元数据写有 JM 号、卷号和页数。

**“在线阅读”按钮：** `web_app` 类型的按钮只能用在和 Bot 的私聊里，所以频道帖子改用普通链接按钮，指向 `https://t.me/<bot>?startapp=<photo_id>`。点击后会直接在 Telegram 里打开这一本的阅读页。前提是先在 BotFather 里给 Bot 设置 Main Mini App。

**在 Telegram 客户端里怎么看：**

- **在线阅读：** 点按钮打开 Mini App，从第 1 页或上次读到的位置继续。
- **下载整本：** 点帖子里的 CBZ 文件。Telegram 不能直接翻看 CBZ，安卓端会下载整本后交给外部漫画 App 打开。
- 按页读取是服务器读频道文件的方式，不改动频道里的文件，所以以上两种看法都不受影响。

**为什么用频道，而不是和 Bot 的私聊：**

| 方面 | 存在私聊里 | 存在私有频道里 |
| --- | --- | --- |
| 内容 | 书和搜索结果、进度消息混在一起 | 只放书，一本一条帖子，像书架 |
| 误删 | 私聊里删除对话或清空记录时，可以勾选“同时为对方删除”，书库会被一起删掉 | 只有管理员能删；清理私聊不影响书库 |
| 查找 | 要在对话记录里翻 | 可以在频道内搜 `#JM123456`，“文件”标签页可以按书浏览 |
| 多人使用 | 每个人的私聊是分开的，要给每人各发一份 | 把人拉进频道即可 |
| 通知 | 每入库一本都会响 | 频道可以单独静音 |

这两种方式 Bot 都能存、能取，技术上没有区别；分开存放是为了安全和方便浏览。

## 4. 阅读流程

1. 用户点开 Mini App，入口有两个：私聊里 Bot 发的 `web_app` 按钮，或者频道帖子上的链接按钮。
2. 页面把 Telegram 提供的 `initData` 发给服务器。服务器依次检查：
   - 用 Bot Token 计算的 HMAC 签名正确；
   - `auth_date` 没有过期；
   - 用户 ID 在白名单里。
   通过后，服务器发一个 HttpOnly 会话 Cookie，建议有效期 12 小时。之后的 `<img>` 请求都靠这个 Cookie 鉴权。
3. 图片请求 `GET /p/{photo_id}/{n}` 的处理顺序：
   1. 先查本地页面缓存。缓存放在磁盘上，按最近最少使用淘汰，上限建议 1GB。
   2. 没命中，就按 `pages` 表里的偏移，用 Telethon 从频道消息下载这一段字节，写入缓存后返回。
   3. 同时在后台预取后面 5–10 页。
4. 页面滚动时，按一定间隔上报 `(用户, 章节, 页码)`。下次打开从这一页继续。
5. 响应头设为 `Cache-Control: private, max-age=...`：手机 WebView 会缓存图片，Cloudflare 不会缓存。

**补充说明：**

- **阅读方式：** 默认上下滑动，图片按需加载；可以切换成左右翻页。每个用户的选择分别保存。
- **文件引用过期：** 频道消息里的文件引用（file_reference）会过期。按 `(频道, 消息 ID)` 重新获取一次消息就能刷新。进程里可以把消息对象缓存 1 小时左右。
- **实测延迟：** Bot 在 DC1（迈阿密），是离本机最近的 DC。把一页拆成 128KB 的块并行读取，单页中位数 178ms；并行预取 10 页约 1.1 秒。详见 [environment.md](environment.md) 第 7 节。

### Mini App 页面结构

顶部有三个标签，从左到右：书架 ｜ 搜索 ｜ 任务。

- **书架：** 已入库的作品，可以按“全部 / 已收藏 / 未收藏”筛选，也可以按收藏夹分组查看。
- **搜索：** 功能和给 Bot 发消息相同：
  - 输入关键词就搜索，结果每页 80 条，往下滑自动加载。
  - JM 号、`#JM`、作品链接、全角数字都能识别；一次输入多个号码时，按输入顺序列出这几本，并提供“全部入库”“全部收藏”。
  - 点进作品后，可以入库、收藏、在线阅读；正在入库时每 5 秒刷新一次状态。
- **任务：** 显示最近 40 个任务的状态、进度和失败原因，每 3 秒自动刷新。
- **封面：** 没入库作品的封面由服务器代取 JM 竖版图（手机直连 JM 很慢），缓存在页面缓存目录里，最多 5000 张。
- **安全：** 所有接口都要求登录令牌，书架里能做的操作和 Bot 一样，不会多出权限。在书架里发起的入库，私聊里照样会收到进度消息。

## 5. 入库流程

任务状态依次为 `queued`、`fetching`、`packing`、`uploading`、`done`。出错时进入 `failed` 并记录原因，最多自动重试 3 次，间隔逐次加长。

多章节作品默认把所有章节一起入库：每章一个任务，按章节顺序执行，帖子也按顺序发到书库频道。

1. **去重：** 如果同一个 photo_id 已经有频道消息 ID，就直接返回已有记录。
2. **检查磁盘：** 剩余空间不够“预计大小 × 2 + 1GB”时，拒绝开始并提示用户。
3. **下载：** 在子进程里运行 jmcomic，下载到 `work/{job_id}/`。配置为 `client.impl: api`、`download.threading.image: 4`。
4. **打包：** 生成 CBZ，写入 `ComicInfo.xml`，记录每页偏移，计算 sha256。
5. **上传：** 用 Telethon 并行分块上传到频道，每块 512KB，4 路并发，实测约 7MB/s（Telethon 默认的顺序上传只有 0.8MB/s）。上传过程中，大约每 5 秒更新一次 Bot 消息里的进度。
6. **收尾：** 在一个事务里写入数据库，然后删除工作目录。前几页可以留在页面缓存里，方便马上阅读。

**调度规则：**

- 同一时间只跑一个任务，因为服务器只有 1 个 vCPU。
- 服务重启后，停在 `fetching`、`packing`、`uploading` 的任务会退回 `queued` 重新执行。上传前会先查去重，所以不会重复上传。

## 6. 精选收藏（PDF 发到精选频道）

**做法：** 另建一个私有频道作“精选频道”，Bot 同样设为管理员。收藏时，把作品转成 PDF 发进去。它和书库频道用的是同一种存储方式，只是改存 PDF、单独归类。

**收藏和收藏夹（v1.1）：**

- “收藏”的意思是：作品在某个用户的任意一个收藏夹里。每个用户都有一个“默认收藏夹”，可以再自建收藏夹，同一本可以放进多个收藏夹。
- 被收藏的作品如果还没入库，就先自动入库；入库完成后，自动生成 PDF 发到精选频道。每本只生成一份 PDF。
- 取消收藏只是移出收藏夹，精选频道里的 PDF 保留不删，以免误删。确实要删时，用 `/remove`。
- 第一版里已经生成 PDF 的作品，升级时会自动迁移进所有者的默认收藏夹。
- JM 账号的收藏夹同步进来后，变成“JM·<名字>”收藏夹，规则见第 12 节。

**为什么这样选：**

- 不花钱，不用开新账号，没有容量上限，单个文件最大 2000MB。
- 在 Telegram 里点开 PDF 就能看，不需要装别的 App。
- 上传速度已实测，并行约 7MB/s。

**代价：** 精选频道和书库频道都在 Telegram 上，算不上独立备份。如果 Telegram 删了频道或封了账号，两边会一起受影响。以后需要独立备份时，再另选外部存储，例如 MEGA、自建 Komga、R2 或 B2。

**流程：**

1. 从书库频道把这本作品的所有章节下载到临时目录，并行下载。
2. 把 WebP 转成 JPEG（质量 85），再用 img2pdf 原样封装成 PDF。PDF 不能直接嵌入 WebP，所以要先转。PDF 里写入标题、作者等元数据。
   - 实测 53 页：质量 85 约 29MB，质量 92 约 37MB，原 WebP 22MB。
   - 转换耗时 4–5 秒，峰值内存 134–153MB。
3. 一本作品合成一个 PDF，章节按顺序排列；超过 2000MB 时分卷。
4. 并行分块上传到精选频道。帖子说明带标题和 `#JM号`，方便搜索。JM 号和卷号写在 PDF 的 Subject 元数据里。
5. 记录消息 ID 和 sha256，然后删除临时文件。

**去重：** 同一本已经收藏过的，直接给出原帖链接，不重复上传。

## 7. 数据与备份

SQLite 使用 WAL 模式，表结构如下：

| 表 | 主要字段 |
| --- | --- |
| `albums` | jm_id、标题、作者、标签、章节数、页数、入库时间 |
| `chapters` | photo_id、jm_id、序号、标题、页数、频道消息 ID、文件大小、sha256 |
| `pages` | photo_id、页序号、文件名、数据偏移、长度 |
| `jobs` | id、类型（archive / favorite）、目标、状态、尝试次数、错误、进度消息、所属批次、时间戳 |
| `batches` | 批量任务（多个 JM 号、JM 同步），共用一条进度消息 |
| `progress` | 用户 ID、jm_id、photo_id、页码、更新时间 |
| `favorites` | PDF 记录（表名沿用第一版）：jm_id、精选频道消息 ID、文件大小、sha256、生成人、上传时间 |
| `folders` | 收藏夹：所属用户、名字、来源（local / jm）、对应的 JM 收藏夹 ID、是否默认 |
| `folder_items` | 收藏夹 ID、jm_id、加入时间 |
| `users` | Telegram 用户 ID、角色（所有者 / 普通用户）、阅读方式、添加时间 |

**书架数据存在哪里：**

- 书目、章节、每页偏移、收藏夹、阅读进度：服务器上的 SQLite 数据库。
- 封面：服务器磁盘。
- 漫画文件本身：Telegram 频道，存在 Telegram 自己的数据中心里（Bot 在 DC1，迈阿密）。
- 页面缓存：服务器上只保留最近看过的页面，上限 1GB。

**备份：** 每天用 `sqlite3 .backup` 生成一份一致的数据库快照，压缩后作为文件发到同一个私有频道，只保留最近若干份。

**元数据文件（v1.1）：** 每本作品在 `/var/lib/jmcomic/meta/JM<号>.json` 另存一份完整元数据，内容包括：书目、各章的频道消息 ID、大小、sha256、每页偏移和尺寸、PDF 记录、所在收藏夹。

- 这些文件在入库、生成 PDF、收藏夹变化时自动更新，一本约 2–5KB。
- 迁移或恢复时直接用 `python -m jmshelf restore-meta <目录>` 重建数据库，不需要扫描频道。

**从频道重建（最后手段）：**

1. Telegram 不允许 Bot 翻阅频道历史，但允许 Bot 按消息 ID 批量取消息（每次 100 条）。所以从 1 号消息扫到最新 ID，找出其中的 CBZ 文件。
2. 每个 CBZ 只需按区间读两小段：末尾的 ZIP 中央目录，以及里面的 `ComicInfo.xml`。前者可以重新算出每页偏移，恢复 `pages` 表；后者有 JM 号、章节和页数，可以恢复 `albums` 和 `chapters` 表。
3. 精选频道的 PDF 只需读一次文件元数据，就能恢复 `favorites` 表。

## 8. 安全

- **密钥不进仓库：** 本仓库是公开的。Token、api_hash、两个频道的 ID、用户 ID、会话文件、数据库和 Cookie 密钥一律不提交，放在服务器的 `/etc/jmcomic/`（600 权限），或者用 systemd 的 `EnvironmentFile` 加载。
- **白名单：** 所有者的 Telegram 用户 ID 写在配置文件里；其他用户存在 `users` 表里，由所有者在 Bot 里用命令增删。白名单以外的人发消息，Bot 不回应。
- **Web 访问：**
  - 服务只监听 127.0.0.1；nginx 沿用现有规则，只放行 Cloudflare 回源。
  - 所有接口都要求会话 Cookie。
  - 图片接口按 photo_id 和页码访问，不暴露服务器上的文件路径。
- **会话文件：** Telethon 的会话文件相当于 Bot 的登录凭证，要设为 600 权限。丢了可以用 Token 重新登录。
- **频道：** 保持私有，不生成邀请链接。
- **服务权限：** 用专用的系统用户运行服务。systemd 里加上 `NoNewPrivileges`、`ProtectSystem=strict`，并用 `MemoryMax` 限制内存。

## 9. 资源预算

本机有 1 vCPU、1.9GB 内存，剩余磁盘约 5.1GB。

| 项目 | 预算 |
| --- | --- |
| 主服务常驻内存 | 约 100–150MB（估算，阶段 0 实测） |
| 下载子进程 | 4 线程实测峰值 294MB；systemd 限制 600MB |
| 页面缓存 | 1GB，最近最少使用的先淘汰 |
| 工作目录 | 同一时间一个任务，通常小于 500MB，任务完成即删 |
| 磁盘保底 | 剩余空间低于 1.5GB 时暂停接新任务 |

## 10. Bot 交互与消息格式

**命令：**

- `/search 关键词`，或直接发关键词：返回搜索结果，已入库的会标出来。
- 直接发 JM 号：显示带封面的作品详情，下方有入库、在线阅读、收藏或取消收藏按钮。各种写法的识别规则见 `jmshelf/ids.py`。
- 一条消息里有多个 JM 号：先列出每本的标题和状态，再给出“全部入库”“全部收藏”按钮。
- `/library`：打开 Mini App 书架。
- `/jobs`：查看当前任务队列。
- 所有者专用：
  - `/status`：查看版本、磁盘、缓存、队列，以及最近一次自动更新的结果。
  - `/jmsync`：同步 JM 收藏夹。
  - `/users`、`/adduser`、`/deluser`：管理用户。
  - `/remove`：从书库删除一本。

**“在线阅读”的行为：** 私聊、书库帖子、PDF 帖子上的“在线阅读”都直接打开阅读器，从上次读到的位置继续，不经过书架。在阅读器里点返回，会回到作品页。

**消息格式**（与本人其他 Bot 保持一致）：

- 不使用表情符号。
- 表格放在 `<code>` 里：表头下面一行虚线，列之间空两格，数字右对齐。
- 表格里只用 ASCII 字符，宽度控制在 40 个字符左右；中文标题和说明写在表格外。

## 11. 部署

| 项目 | 做法 |
| --- | --- |

## 12. JM 收藏夹同步与自动更新（v1.1）

### JM 收藏夹同步（`jmshelf/sync.py`）

- **账号：** 把 JM 账号写进服务器配置的 `JM_USERNAME`、`JM_PASSWORD`。密码只保存在这台服务器上。
- **手动同步：** `/jmsync` 先登录，读出所有收藏夹，列出每个收藏夹的本数，以及同步后要入库多少本、生成多少份 PDF。确认后才开始。
- **同步规则：** 单向镜像，从 JM 到本地：
  - JM 里的每个收藏夹，对应本地一个“JM·<名字>”收藏夹。
  - 不在任何收藏夹里的收藏，归到“JM·未分类”。
  - JM 那边移除的作品，从对应的“JM·”收藏夹移出；JM 那边删掉的收藏夹，本地也删掉。
  - 本地自建的收藏夹、书库里的作品和 PDF 都不受影响。
- **新收藏的作品：** 入库后自动生成 PDF，用一个批次执行，只发一条进度消息。
- **自动同步：** 在 `/jmsync` 里可以打开“每天自动同步”，之后服务每 24 小时同步一次。失败时在私聊里提醒。

### 反向同步到 JM（默认关闭）

- **开关：** 在 `/jmsync` 的消息里，和“每天自动同步”并排，由所有者控制。
- **触发：** 所有者在这边新收藏一本时，会在后台加进 JM 账号的收藏。三处操作都会触发：Bot 里点“收藏”、书架里勾选收藏夹、批量“全部收藏”。
- **只加不删：** 在这边取消收藏，不会从 JM 删除。其他用户的收藏也不会推送，因为 JM 账号是所有者的。
- **接口限制：** JM 移动端的收藏接口是“切换”：对已收藏的作品再调用，会先取消、再由 jmcomic 回滚，可能打乱它在 JM 收藏夹里的位置。所以每次推送前先读一遍 JM 现有收藏，已收藏的直接跳过。移动端接口不支持指定收藏夹，新加的都进默认收藏。下次正向同步时，这些作品会出现在“JM·未分类”里。
- **结果：** 失败时私聊通知；最近一次的结果在 `/jmsync` 和 `/status` 里显示。

### jmcomic 自动更新（`deploy/jmcomic-update.sh`）

**什么时候检查：**

- 每天 04:30（北京时间），由 `jmcomic-update.timer` 触发。
- 下载出错时，服务会写一个请求文件，由 `jmcomic-update.path` 立即触发一次检查。6 小时内最多触发一次。

**升级规则：**

- 只自动升级同一个大版本内的新版本。大版本（例如 3.x）只私聊提醒，不自动升级。
- 依赖写的是 `jmcomic>=2.7.10,<3`，所以重新部署也不会把自动升级的版本降回去。

**升级步骤：**

1. 等正在执行的任务结束，最多等 30 分钟。
2. 停服务。
3. 升级。
4. 运行自检 `python -m jmshelf.selftest`：搜索、取详情、下载并解码两张图片。
5. 自检通过就启动服务；不通过就装回原版本再启动。

**结果：** 写入 `update-status.json`，在 `/status` 里能看到。有升级、回滚或需要人工处理时，私聊通知所有者。

**实测：** 把版本临时降到 2.7.9，自动升级回 2.7.10，全程 19 秒，自检通过，服务正常重启。

**不自动升级的依赖：** Telethon 等其他依赖保持固定版本，因为之前遇到过 Telegram 协议更新导致按钮类型改名。需要升级时人工处理。
