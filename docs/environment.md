# 目标服务器环境与可行性实测

实测日期：2026-10-23。目标服务器是一台洛杉矶 VPS。本仓库是公开仓库，所以本文不记录 IP、端口、其他服务和具体域名。

## 1. 服务器资源

| 项目 | 情况 |
| --- | --- |
| 系统 | Ubuntu 24.04.5 LTS，Python 3.12.3 |
| CPU | 1 vCPU |
| 内存 | 1.9GB，日常可用约 1.0GB，另有 2GB swap |
| 磁盘 | 20GB，剩余约 5.1GB |
| Web 入口 | nginx 已占用 80/443，已有本域名的 Cloudflare 源站通配证书，已配置“只允许 Cloudflare 回源” |
| 其他 | 已有 Docker 和若干常驻服务；`cloudflared`、`uv` 未安装 |

**结论：** 这台机器适合做下载、打包和转发，不适合放大缓存，也不适合自建 Bot API Server。下载任务要串行执行，并限制线程数。

## 2. Telegram 网络

数据来自 2026-10-17 的路由检测（TCP 层测试，IPv4/IPv6 分开测）：

| 目标 | IPv4 | IPv6 |
| --- | --- | --- |
| DC1 / DC3（迈阿密） | 约 72ms，0 丢包 | 正常 |
| DC2 / DC4（阿姆斯特丹）、api.telegram.org | 约 150ms，0 丢包 | **新连接间歇性失败 4%–18%** |
| DC5（新加坡） | 约 170ms，0 丢包 | 正常 |

**对本项目的影响：**

- Telethon 默认 `use_ipv6=False`，MTProto 连接天然只走 IPv4，不受影响。
- 如果另外用 HTTP 访问 `api.telegram.org`（例如 python-telegram-bot），必须把出站强制成 IPv4。
- 每次读取一页都有一个往返的延迟，具体数值取决于 Bot 文件所在的 DC，需要在阶段 0 实测。

## 3. JM 连通性

工具为 `jmcomic` 2.7.10，以下数据在本机实测得到：

| 测试 | 结果 |
| --- | --- |
| 移动端 API（`client.impl: api`，库默认值） | 正常：建客户端 1.5s，搜索 0.9s，取本子详情 0.7s |
| 网页端（`client.impl: html`） | **403**：“ip地区禁止访问/爬虫被识别” |
| 图片 CDN（走 Cloudflare） | IPv4/IPv6 都可用；单张 50–160ms，速度 3–10MB/s |
| 整本下载并解码（53 页） | 4 线程：17.8s，峰值内存 294MB |
| 同上 | 8 线程：18.5s，峰值内存 533MB |
| 产出 | 53 张 WebP，共 22MB，单页 170–720KB |

**结论：**

- 只用 API 端，不要配置 html 端。
- 图片线程设为 2–4。在 1 vCPU 上瓶颈是解码，线程开得多并不会更快，只会多占内存（库默认是 20 线程）。
- jmcomic 解码后用 Pillow 默认参数重新保存图片，WebP 的质量是 80。如果在意画质，可以在阶段 0 改成更高质量，并比较文件体积。

## 4. Telegram 文件通道对比

| 通道 | 上传上限 | 下载上限 | 能否只读文件的一部分 |
| --- | --- | --- | --- |
| 官方 Bot API（api.telegram.org） | 50MB | 20MB | 不能 |
| 自建 Bot API Server（`--local`） | 2000MB | 不限 | 不能，`getFile` 会先把整个文件下载到本机 |
| MTProto（Telethon，Bot 账号） | 2000MB | 不限 | 能，可以从指定字节偏移开始下载 |

53 页的本子已经有 22MB，所以长篇或多图的本子会超过官方 Bot API 的限制。

## 5. CBZ 按页读取验证

验证步骤如下：

1. 把上面 53 页打包成 CBZ（ZIP 不压缩，即 `ZIP_STORED`），加上 `ComicInfo.xml` 共 54 个成员，文件约 21MB。
2. 根据每个成员的本地文件头算出数据起始偏移。
3. 直接按字节区间读出每个成员，与 `zipfile` 解压结果比较。

结果：54 个成员全部一致。所以入库时记下每页的偏移和长度，阅读时只读那一段就能拿到这一页，不需要下载整本。

测试用的图片和 CBZ 在验证后已经删除。
