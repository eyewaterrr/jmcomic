# 目标服务器环境与可行性实测

实测日期：2026-10-23。目标服务器是一台洛杉矶 VPS。本仓库是公开仓库，所以本文不记录 IP、端口、其他服务和具体域名。

## 1. 服务器资源

| 项目 | 情况 |
| --- | --- |
| 系统 | Ubuntu 24.04.5 LTS，Python 3.12.3 |
| CPU | 1 vCPU |
| 内存 | 1.9GB，日常可用约 1.0GB，另有 2GB swap |
| 磁盘 | 20GB，剩余约 5.1GB |
| Web 入口 | nginx 已占用 80/443，已有本域名的 Cloudflare 源站通配证书，已配置“只允许 Cloudflare 回源” |
| 其他 | 已有 Docker 和若干常驻服务；`cloudflared`、`uv` 未安装 |

**结论：** 这台机器适合做下载、打包和转发，不适合放大缓存，也不适合自建 Bot API Server。下载任务要串行执行，并限制线程数。

## 2. Telegram 网络

数据来自 2026-10-17 的路由检测（TCP 层测试，IPv4/IPv6 分开测）：

| 目标 | IPv4 | IPv6 |
| --- | --- | --- |
| DC1 / DC3（迈阿密） | 约 72ms，0 丢包 | 正常 |
| DC2 / DC4（阿姆斯特丹）、api.telegram.org | 约 150ms，0 丢包 | **新连接间歇性失败 4%–18%** |
| DC5（新加坡） | 约 170ms，0 丢包 | 正常 |

**对本项目的影响：**

- Telethon 默认 `use_ipv6=False`，MTProto 连接天然只走 IPv4，不受影响。
- 如果另外用 HTTP 访问 `api.telegram.org`（例如 python-telegram-bot），必须把出站强制成 IPv4。
- 每次读取一页都有一个往返的延迟，具体数值取决于 Bot 文件所在的 DC，需要在阶段 0 实测。

## 3. JM 连通性

工具为 `jmcomic` 2.7.10，以下数据在本机实测得到：

| 测试 | 结果 |
| --- | --- |
| 移动端 API（`client.impl: api`，库默认值） | 正常：建客户端 1.5s，搜索 0.9s，取本子详情 0.7s |
| 网页端（`client.impl: html`） | **403**：“ip地区禁止访问/爬虫被识别” |
| 图片 CDN（走 Cloudflare） | IPv4/IPv6 都可用；单张 50–160ms，速度 3–10MB/s |
| 整本下载并解码（53 页） | 4 线程：17.8s，峰值内存 294MB |
| 同上 | 8 线程：18.5s，峰值内存 533MB |
| 产出 | 53 张 WebP，共 22MB，单页 170–720KB |

**结论：**

- 只用 API 端，不要配置 html 端。
- 图片线程设为 2–4。在 1 vCPU 上瓶颈是解码，线程开得多并不会更快，只会多占内存（库默认是 20 线程）。
- jmcomic 解码后用 Pillow 默认参数重新保存图片，WebP 的质量是 80。如果在意画质，可以在阶段 0 改成更高质量，并比较文件体积。

## 4. Telegram 文件通道对比

| 通道 | 上传上限 | 下载上限 | 能否只读文件的一部分 |
| --- | --- | --- | --- |
| 官方 Bot API（api.telegram.org） | 50MB | 20MB | 不能 |
| 自建 Bot API Server（`--local`） | 2000MB | 不限 | 不能，`getFile` 会先把整个文件下载到本机 |
| MTProto（Telethon，Bot 账号） | 2000MB | 不限 | 能，可以从指定字节偏移开始下载 |

53 页的本子已经有 22MB，所以长篇或多图的本子会超过官方 Bot API 的限制。

## 5. CBZ 按页读取验证

验证步骤如下：

1. 把上面 53 页打包成 CBZ（ZIP 不压缩，即 `ZIP_STORED`），加上 `ComicInfo.xml` 共 54 个成员，文件约 21MB。
2. 根据每个成员的本地文件头算出数据起始偏移。
3. 直接按字节区间读出每个成员，与 `zipfile` 解压结果比较。

结果：54 个成员全部一致。所以入库时记下每页的偏移和长度，阅读时只读那一段就能拿到这一页，不需要下载整本。

测试用的图片和 CBZ 在验证后已经删除。

## 7. Telegram 存储实测（阶段 0，2026-10-24）

**测试方法：**

1. 用随机数据生成 CBZ，每页 400KB，无法压缩。
2. 上传到私有频道。
3. 按页读回，逐字节核对。
4. 测完删除测试消息。

**结果：**

| 项目 | 结果 |
| --- | --- |
| Bot 所在 DC | DC1（迈阿密），本机约 72ms，是五个 DC 中最近的 |
| 连接 | MTProto 走 IPv4；首次登录 5.2s，之后获取频道 0.14s |
| 上传：Telethon 默认（顺序） | 0.8MB/s，20MB 用 26.6s，100MB 用 133.3s |
| 上传：并行分块（512KB，4 / 8 / 16 路） | 6.7 / 7.1 / 6.8MB/s，20MB 约 3s |
| 重新获取消息（刷新文件引用） | 约 85ms |
| 按页读取：512KB 对齐，顺序请求 | 首页 272–662ms，之后中位数 282–328ms |
| 按页读取：128KB 对齐，分块并行 | 中位数 178ms，最大 380ms |
| 并行预取 10 页 | 约 1.1s |
| 整本下载（100MB，顺序） | 3.7MB/s，27.3s |
| 进程峰值内存 | 168MB（含测试脚本放在内存里的 100MB 原始数据） |

**结论：**

- **上传：** 必须并行分块，4 路就够，100MB 约 15 秒。Telethon 默认的顺序上传太慢。
- **按页读取：** 拆成 128KB 的块并行读，单页约 0.2 秒；加上预取，翻页基本不用等。
- **整本下载：** 转 PDF 时要下载整本，也可以改成并行来提速。

## 9. 分布式下载评估（2026-10-24，已采用远程下载机）

**瓶颈：** 入库慢在本机只有 1 核 CPU。下载后要把打乱的图片拼回原样，再重新压缩保存，约 0.5 秒/页。入库时实测：CPU 100% 占满，等待磁盘为 0，网络下行平均只有约 0.3MB/s，远低于 JM 图片服务器能提供的 3–10MB/s。

**评估过的几种做法：**

| 方案 | 实测或依据 | 结论 |
| --- | --- | --- |
| 国内一台闲置的 Windows 电脑（10 核 16 线程，32GB 内存） | 经代理用 16 线程下载 53 页（21MB）只要 11.4 秒，比本机快；但打包好的文件要传回海外：走 Tailscale（UDP）只有 0.10MB/s，走公网 TCP 约 1.6MB/s。CPU 上省下的时间，又花在了跨境网络上 | 单本不会更快，批量大约快一倍，不值得多维护一台机器 |
| 国内校园网的一台工作站（24 线程，188GB 内存） | 校园网直连就能访问 JM，48 线程下 970 页只要 46 秒。公网传回本机约 11MB/s，Tailscale 经香港中继只有约 1.8MB/s。但校园网挡住了海外发起的连接，只能由它主动连本机；校园网登录过期就会断网 | 最快，但连接受校园网限制，不适合长期使用 |
| 新加坡 Oracle ARM（4 核，23GB 内存） | 见下文 | **采用** |
| 同城的几台 VPS（与本机延迟 1–5ms） | 没有跨境问题，理论上能按核数成倍提速 | 可行，但这些服务器不一定长期续费，暂不做 |
| Google Colab 免费版 | 官方 FAQ 明确禁止运行分布式计算节点；只为有人在网页上操作的场景设计，最长 12 小时，空闲会断开；还要用 Google 账号 | 不能用 |
| GitHub Actions、函数计算、按小时租的云服务器 | 服务条款不允许，或者配置和账号成本高 | 不建议 |

**新加坡 Oracle 实测：**

- **访问 JM：** 按默认 DNS 访问 JM 的 Cloudflare 节点会绕到很远的地方，握手 160ms 以上，还经常超时，52 页要 82 秒。把 JM 域名固定到另一段 Cloudflare IP 后，握手约 1.5ms，单张图 50–75ms，52 页只要 6 秒。
- **与本机之间：** 本机能主动 SSH 进去。公网 SSH 单连接约 8MB/s，4 路并行约 18MB/s。Tailscale 在这条线路上是直连，速度和公网差不多。本机接收 115MB 只花约 0.75 秒 CPU。
- **CBZ 和原图：** CBZ 约是 JM 原图的 1.3 倍（解码后按 WebP 质量 90 重新保存）。

**下载解码速度：**

| 章节 | 本机（4 线程） | 新加坡 Oracle（16 线程） |
| --- | --- | --- |
| 52 页 / 11MB | 13.2 秒 | 6.1 秒 |
| 101 页 / 46MB | 41.2 秒 | 13.4 秒 |
| 970 页 / 115MB | 约 400 秒 | 59 秒，4 核跑满 |

两台机器每页花的 CPU 时间差不多（Oracle 的 ARM 单核还慢一些），快在 4 核并行。GPU 帮不上忙：耗时在 WebP 解码和编码，没有对应的硬件编解码器。

**接入后的端到端实测：** 包括本机先下 8 页估算、交给远程、传回、建索引。

| 章节 | 全在本机 | 分流后 |
| --- | --- | --- |
| 970 页 / 115MB | 约 400 秒 | 76 秒，第 3.5 秒交给远程 |
| 101 页 / 46MB | 32 秒 | 28 秒，第 4 秒交给远程 |
| 52 页 / 11MB、130 页 / 12MB | 11–19 秒 | 留在本机，和原来一样 |

**结论：** 用新加坡 Oracle 做远程下载机，只处理估算达到 30MB 的章节，设计见 [architecture.md](architecture.md) 第 13 节。节省的时间主要取决于页数：970 页的章节快 5 倍；一百页左右、三四十 MB 的章节只快几秒，但这段时间本机 CPU 是空闲的，不影响 Bot 和阅读页。
